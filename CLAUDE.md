# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hexagonal is a word-search game (Spelling Bee/Bonza-style) built with Svelte 5 + TypeScript + Vite. Players drag across a hexagonal letter grid to spell words from that day's deterministically generated word list.

## Commands

```bash
npm run dev      # start Vite dev server (port 5173)
npm run build    # production build (runs `vite build`; no separate typecheck step)
npm run preview  # preview a production build
npm run check    # svelte-check (src/**/*.svelte, *.ts) + tsc -p tsconfig.node.json (noEmit set in that config)
npm run test     # Vitest — currently just src/lib/boardConstruction.test.ts, not a general suite
npm run bench    # Vitest benchmarks — currently just src/lib/boardConstruction.bench.ts
```

`dev`/`build`/`check`/`test`/`bench` each run `words:generate` first (via `predev`/`prebuild`/`precheck`/`pretest`/`prebench`), which regenerates the dictionary from SCOWL into `.cache/scowl/` — see [src/lib/dictionary.ts](src/lib/dictionary.ts). The first run needs network access and `make`, and takes roughly a minute; subsequent runs reuse the cached download/build and are fast. `predev` additionally runs `puzzles:generate:local`, which generates today's/tomorrow's puzzle files under `public/puzzles/` if they're not already there — see "Puzzle pre-generation" under Notable Patterns below for why `prebuild`/`precheck` deliberately don't do the same.

There's no linter/formatter configured. `npm run check` is the correctness gate for everything (types only — layout/interaction bugs like a reflow triggered by content changes can type-check cleanly and still be broken, so UI/layout changes need manual browser verification too). `npm run test`/`npm run bench` (Vitest) exist specifically for `boardConstruction.ts`'s backtracking placement algorithm, whose correctness (does it ever fail to fill the board?) and performance (it runs synchronously at page load, with no loading state) aren't things type-checking or manual play-testing can catch — this isn't yet a general test suite for the rest of the codebase.

## Architecture

- [src/lib/hexGeometry.ts](src/lib/hexGeometry.ts) — pure geometry/data functions: axial coordinate generation (`generateHexCoords`), adjacency (`areAdjacent`), axial→pixel projection, SVG hex polygon points, and viewBox computation. Also owns the core types `AxialCoord`, `Tile`, `WordSubmission`. Everything here is framework-agnostic and easily unit-testable in isolation if tests are ever added.
- [src/lib/dailyPuzzle.ts](src/lib/dailyPuzzle.ts) — generation-only; not part of the client bundle. `generateDailyPuzzle(date)` deterministically builds a day's board and computes the full valid-word answer key from scratch, seeded by that date in Mountain Time (via [src/lib/prng.ts](src/lib/prng.ts)'s `seedForDate`/`mulberry32`). `toPuzzleFileData` shapes the result (plus each word's frozen common/rare tag) into the on-disk schema. The only caller is [scripts/generatePuzzles.ts](scripts/generatePuzzles.ts) — see "Puzzle pre-generation" below; `App.svelte` never calls this directly.
  - [src/lib/dictionary.ts](src/lib/dictionary.ts) — loads the generated word list (`.cache/scowl/words.txt`, produced by [scripts/generateWordLists.py](scripts/generateWordLists.py) from SCOWL v2, gitignored/not bundled — see that script's docstring) and filters it to the tunable `MIN_WORD_LENGTH`/`MAX_WORD_LENGTH` bounds (currently 3–19). The source file itself is never pre-filtered, so those bounds can change without regenerating anything. Also exposes each word's binary common/rare rarity tag via `loadWordRarities()`, consumed only at generation time (by `boardConstruction.ts` and `toPuzzleFileData`) — `scoring.ts` no longer reads this module; see "Puzzle pre-generation" below. Offensive-word filtering (SCOWL's profanity/slur usage-note tags, the LDNOOBW list, and hand-maintained `scripts/wordBlacklist.txt`/`scripts/wordWhitelist.txt`) happens upstream in `generateWordLists.py`, not in this file.
  - [src/lib/boardConstruction.ts](src/lib/boardConstruction.ts) — `buildBoard` fills the board via constructive backtracking placement: it repeatedly picks a weighted-random word (favoring longer and more letter-reusing words — see the tunable constants at the top of the file) and a weighted-random adjacent-tile path for it (considering placements anchored from either end of the word, not just the first letter, so reuse near the end of a word is found as readily as reuse near the start), fills in any still-empty tiles along that path, and recurses into itself for the next word. On failure it undoes the placement and tries the next path/word, backtracking until every tile is covered by at least one placed word. Word candidates are restricted to SCOWL's common tier (via `loadWordRarities()`), not the full eligible dictionary — deliberately planted words should be recognizable, and the smaller pool keeps the one-time word-ranking pass cheap; `wordSolver.ts` still scores the finished board against the full dictionary, so rare words can still turn up as incidental bonus finds. Throws if the search is genuinely exhausted without success — not a fallback, since no precondition check is performed before attempting; the search itself is exhaustive. Covered by [src/lib/boardConstruction.test.ts](src/lib/boardConstruction.test.ts) (`npm run test`) and [src/lib/boardConstruction.bench.ts](src/lib/boardConstruction.bench.ts) (`npm run bench`).
  - [src/lib/wordSolver.ts](src/lib/wordSolver.ts) — `solveBoard` is the real source of the answer key: an exhaustive trie-pruned DFS ([src/lib/trie.ts](src/lib/trie.ts)) over the finished board that finds every valid word (not just the one planted), independently reimplementing (not reusing) `HexGrid.svelte`'s no-revisit-tile rule.
- [src/lib/puzzleLoader.ts](src/lib/puzzleLoader.ts) — client-only; the only puzzle-loading code that's actually part of the app bundle. `loadDailyPuzzle(date)` fetches `public/puzzles/<Mountain-Time date>.json` and hands back tiles/wordList/puzzleId plus a `rareWords` set for `scoring.ts`. `puzzleFromFile` reconstructs `tiles` from `puzzleId` alone (no `tiles` field is stored on disk) by zipping `generateHexCoords(BOARD_RADIUS)` — which emits coordinates in the same ascending-(q,r) order `dailyPuzzle.ts`'s `puzzleIdForTiles` sorts by — against `puzzleId`'s letters. Deliberately imports nothing from `dailyPuzzle.ts`/`dictionary.ts`/`boardConstruction.ts`/`wordSolver.ts`/`trie.ts`, so none of that generation-only code (or the dictionary text it pulls in) ends up in the client bundle. Never falls back to generating a puzzle locally — a fetch failure is a `PuzzleLoadError`, surfaced by `App.svelte` as a visible error state, not silently papered over.
- [src/lib/scoring.ts](src/lib/scoring.ts) — scoring/rarity logic (`getWordScore`, `getCommonWords`, `isRareWord`, completion-bonus checks). Every function takes rarity as an explicit `rareWords: ReadonlySet<string>` parameter (sourced from the loaded puzzle, ultimately `puzzleLoader.ts`) rather than reading a module-level dictionary global — this is what stops a same-day dictionary/blacklist regeneration from silently reshuffling an already-served puzzle's word values or completion-bonus threshold. Callers (`App.svelte`, `Sidebar.svelte`, `SelectionDisplay.svelte`, `wordGrouping.ts`) all thread `rareWords` through as a plain prop/parameter, same as `wordList`/`foundWords`.
- [src/lib/wordGrouping.ts](src/lib/wordGrouping.ts) — pure functions `buildWordEntries`/`groupWordsByLength` used by the sidebar to bucket found/total words by length; take `rareWords` alongside `wordList`/`foundWords` (see `scoring.ts` above).
- [src/lib/HexGrid.svelte](src/lib/HexGrid.svelte) — the interactive board. Owns all pointer-drag selection state (`selection`, `hasMoved`) and renders the SVG hex tiles + selection polyline. Selection is drag-only (pointerdown → move across adjacent tiles → release on the last tile to submit); no click/tap-to-select mode exists. Notifies the parent via `onSelectionChange` (live path, for the letters readout) and `onWordSubmit` (on release). Accepts a `rejectedToken` prop (increment-to-trigger) to play a shake animation when the parent determines a submitted word was invalid — the component itself has no notion of word validity.
- [src/App.svelte](src/App.svelte) — top-level state and word validation: holds `foundWords`, checks submissions against a `Set` built from the loaded puzzle's word list, and wires `TitleBar` / `SelectionDisplay` / `HexGrid` / `Sidebar` together. This is the only place that knows what a "valid word" is; `HexGrid` and `Sidebar` are presentation-only.
- [src/lib/SelectionDisplay.svelte](src/lib/SelectionDisplay.svelte) / [src/lib/TitleBar.svelte](src/lib/TitleBar.svelte) / [src/lib/Sidebar.svelte](src/lib/Sidebar.svelte) — presentational, driven by props — though `SelectionDisplay` and `Sidebar` each keep small bits of local UI state (linger timer, grouped-by-length toggle) that don't round-trip through `App`.

### Notable patterns

- **Token props for one-shot animations**: both `HexGrid` (`rejectedToken`) and `SelectionDisplay` (`resultToken`) use an incrementing-counter prop pattern to trigger transient effects (shake/linger) from the parent, since Svelte has no built-in "fire an event" prop. Each snapshots the previous token value into a plain (non-`$state`) variable inside an `$effect` — making it `$state` causes the effect to read and write a tracked value, causing an immediate self-retrigger. See the comments in [HexGrid.svelte](src/lib/HexGrid.svelte) and [SelectionDisplay.svelte](src/lib/SelectionDisplay.svelte) before changing this pattern.
- **Layout stability over content-hugging**: `SelectionDisplay` uses a fixed `height` (not `min-height`) and `Sidebar`'s wrap in `App.svelte` uses a fixed flex-basis on narrow layouts, so that selecting/deselecting or finding more words never shifts the board's position — only window resizing should.
- `prototypes/` contains standalone HTML/CSS experiments from before the Svelte app existed; not part of the build.
- **Color palette isn't centralized**: the background (`#282c34`), accent yellow (`#f4d35e`), and reject red (`#e05555`) are each hardcoded independently in two places apiece (`app.css`/`HexGrid.svelte` for the background; `HexGrid.svelte`/`SelectionDisplay.svelte` for the other two) rather than defined once in a shared `:root`. A palette change today means updating both call sites by hand.
- **Dictionary is generated, not vendored**: `dictionary.ts` imports `.cache/scowl/words.txt` via Vite's `?raw` suffix. That file isn't checked in — `scripts/generateWordLists.py` builds it from SCOWL v2 (download + local SQLite build) as a `predev`/`prebuild`/`precheck` step, and it's only ever read at puzzle-generation time now (see "Puzzle pre-generation" below) — `dictionary.ts` is no longer reachable from the client bundle at all.
- **Async puzzle fetch, not eager module-level state**: `App.svelte` renders immediately with an empty placeholder board (real tile geometry, blank letters) and calls `puzzleLoader.ts`'s `loadDailyPuzzle()` inside `onMount`, swapping in the real board once the fetch resolves (or showing an error state if it rejects — see "Puzzle pre-generation" below). Every piece of state that depends on the loaded puzzle (`wordMap`, `commonWordSet`, restored `foundWords`, initial score/bonus state) is seeded by a one-shot `$effect` keyed on `puzzle` transitioning from `null` to a value, not computed at component setup time.
- **Puzzle pre-generation** (issue #37: a puzzle must never change once served to any player, even across a same-day app redeploy): puzzles are generated by [scripts/generatePuzzles.ts](scripts/generatePuzzles.ts) (run via `vite-node`, since it needs `dailyPuzzle.ts`'s transitive Vite-specific `?raw` import — plain Node/tsc can't resolve that) and committed as `public/puzzles/YYYY-MM-DD.json` (schema: `dailyPuzzle.ts`'s `PuzzleFileData` — `date`, `puzzleId`, and `words: {word, rare}[]`; no `tiles` field, since it's fully reconstructable from `puzzleId` — see `puzzleLoader.ts` above). [.github/workflows/generate-puzzles.yml](.github/workflows/generate-puzzles.yml) runs right at the Mountain-Time day boundary (GitHub Actions' native per-schedule `timezone` field — `cron: "0 0 * * *"` + `timezone: "America/Denver"` — tracks the MST/MDT switch automatically, no manual UTC-offset math) and generates a rolling buffer covering today plus 3 days ahead (idempotent — skips any date whose file already exists), so one missed/late run doesn't cause a same-day outage; this is also why the client never falls back to generating a puzzle itself. Deliberately includes *today*, not just future days: GitHub's scheduled-workflow triggers are best-effort and have been observed running hours late, and the script computes "today" from wall-clock time at execution, so a late-enough run's own "today" has already advanced past the trigger's target day — an offset that assumed "always generate starting tomorrow" would then skip the day that had just started, which bit in production once (see git history around 2026-09-07) before the offset was changed to 0. Locally, `npm run puzzles:generate:local` (wired into `predev` only, not `prebuild`/`precheck`) generates today's and tomorrow's files if missing, so `npm run dev` works with zero manual steps — deliberately **not** wired into `prebuild`/`precheck`, since those run inside `deploy.yml`'s CI job, and a same-day app-code push must never be able to silently generate that day's puzzle as a side effect of building. The one sanctioned same-day mutation is `npm run puzzles:remove-word -- <word>` (`scripts/removeWord.ts`), for an offensive word that slipped past `generateWordLists.py`'s filtering: it strips matching entries from every committed puzzle file's `words` array (never touching `puzzleId`/the board) and appends the word to `scripts/wordBlacklist.txt`, without needing to regenerate anything.

## Svelte 5 conventions used in this codebase

- Runes only (`$state`, `$derived`, `$props`, `$effect`) — no legacy `export let` / reactive `$:` statements.
- Components receive callback props (`onSelectionChange`, `onWordSubmit`) rather than dispatching custom events.
